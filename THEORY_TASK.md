**1)** Пусть на вход дан сигнал x[n], а на выход нужно дать два сигнала y1[n] и y2[n]:

```
 y1[n] = x[n - 1] + x[n] + x[n + 1]
 y2[n] = y2[n - 2] + y2[n - 1] + x[n]
```

Какой из двух сигналов будет проще и быстрее реализовать в модели массового параллелизма на GPU и почему?

```Первый проще```. Первый сигнал хорош тем, что он легко выражается через изначально заданный сигнал и не зависит от каких-либо дополнительных нетривиальных вычислений, второй вообще некорректно задан, там рекуррентная формула без начальных членов, но видимо подразумевается что они заданы. Плюс массового параллелизма в том, что мы можем сделать много параллельный операций, а во втором сигнале у нас в i-й ячейке массива сигнал зависит от предыдущих двух, если наивно реализовывать то придется видимо ставить барьеры, что убьет все плюсы массового параллелизма. Но вообще это не совсем описывает в чем проблема, если просто поразворачивать эту реккуренту, то получится, что y2[i] зависит от всех x[j] с j $\leq$ i, в первой идущей в голову реализации во всяком случае с этом проблемой бороться сложно, либо надо ставить барьеры, либо придется читать все предыдущие x, в общем если делать так то все еще приходится обрабатывать данные последовательно, а не параллельно. Для y1 таких проблем нету, можно спокойно складывать нужные чиселки параллельно.


**2)** Предположим что размер warp/wavefront равен 32 и рабочая группа делится
на warp/wavefront-ы таким образом что внутри warp/wavefront
номер WorkItem по оси x меняется чаще всего, затем по оси y и затем по оси z.

Напоминание: инструкция исполняется (пусть и отмаскированно) в каждом потоке warp/wavefront если хотя бы один поток выполняет эту инструкцию неотмаскированно. Если не все потоки выполняют эту инструкцию неотмаскированно - происходит т.н. code divergence.

Пусть размер рабочей группы (32, 32, 1)

```
int idx = get_local_id(1) + get_local_size(1) * get_local_id(0);
if (idx % 32 < 16)
    foo();
else
    bar();
```

Произойдет ли code divergence? Почему?

```Нет```. get_local_size(1) должен быть равен 32 (раз у нас размер рабочей группы (32, 32, 1)), номер WorkItem чаще всего меняется по x (который как раз живет в get_local_id(0), а y в get_local_id(1)), значит idx будет чаще всего к индексу получать прибавку 32 (когда по x +1), более редко прибавку 1 (когда по y +1). Тогда получится, что остаток при делении на 32 у idx будет менятся максимально редко (только с прибавкой от y), а значит у нас будет просто первая половина рабочей группы, которая будет полностью исполнятся в блоке if, и вторая половина, которая будет исполнятся в блоке else. Раз у нас размер 32*32, а размер warp тоже 32, то эти половины не пересекутся, а значит все потоки будут выполнять инструкцию неотмаскированно в соответствующем блоке.

**3)** Как и в прошлом задании предположим что размер warp/wavefront равен 32 и рабочая группа делится
на warp/wavefront-ы таким образом что внутри warp/wavefront
номер WorkItem по оси x меняется чаще всего, затем по оси y и затем по оси z.

Пусть размер рабочей группы (32, 32, 1).
Пусть data - указатель на массив float-данных в глобальной видеопамяти идеально выравненный (выравнен по 128 байтам, т.е. data % 128 == 0). И пусть размер кеш линии - 128 байт.

(a)
```
data[get_local_id(0) + get_local_size(0) * get_local_id(1)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

```Да```, ведь внутри одного warp индексы меняются по x, размер warp 32, соответственно внутри одного warp просто одинаковый y и все x является последовательными числами, а значит один warp будет делать запросы к последовательным ячейкам памяти, ведь запрашиваемые индексы в data имеют формулу по сути $x + 32 * y$. Тип данных у нас float, так что скорее всего 4 байта на одно число (хотя вроде стандарт не гарантирует этого, не душите пжпж), поэтому в кэшлинию аккурат влезает 32 float числа, а значит у нас максимально эффективный доступ памяти с точки зрения coalesced (все 32 числа запрашиваются одним warp). В разных warp разные y, а значит в рабочей группе будет 32 запроса, то есть ```32 кэшлинии записей```.

(b)
```
data[get_local_id(1) + get_local_size(1) * get_local_id(0)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

```Нет```, здесь формула доступа уже $y+32 * x$, а значит внутри одного warp будут запрашиваться вообще не пересекающиеся кэшлинии из-за шага в 32 по индексу, а значит 128 в байтах, то есть паттер доступа максимально неэффективный с точки зрения coalesced. В одной рабочей группе таким образом каждый WorkItem будет делать одну запись, а значит получится $32 * 32 = $```1024 кэш линий записей```.

(c)
```
data[1 + get_local_id(0) + get_local_size(0) * get_local_id(1)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

```Частично``` (я так понял что coalesced мы меряем не как да/нет, здесь ближе к да, во всяком случае по сравнению с пунктом (b)), здесь формула индекса почти как в (a): $1 + x  + 32 * y$, а значит внутри одного warp мы запросим 31 число одной кэшлинии, и 1 число следующей, то есть вместо того чтобы делать 1 запрос к памяти, делаем два. Таким образом кэшлиний записей будет в два раза больше чем в (a), то есть ```64```.
