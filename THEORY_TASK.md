**1)** Пусть на вход дан сигнал x[n], а на выход нужно дать два сигнала y1[n] и y2[n]:

```
 y1[n] = x[n - 1] + x[n] + x[n + 1]
 y2[n] = y2[n - 2] + y2[n - 1] + x[n]
```

Какой из двух сигналов будет проще и быстрее реализовать в модели массового параллелизма на GPU и почему?

```text
Ответ:

Сигнал y1[n] реализовать проще, потому что каждый элемент можно вычислить независимо - просто читаем нужные ячейки из x[n]. В случае y2[n] результат зависит от предыдущих значения, что мешает назначить отдельному work item каждый элемент. Возможно, придется вводить какую-то синхронизацию или отказываться от параллельной обработки

Реализация сигнала y1[n] также будет обычно быстрее, потому что надо всего лишь прочитать последовательно неизменяемые значения из x[n]. То есть тут все будет идеально параллелиться, и утилизация кэш-линий будет высокая. В случае y2[n] нам надо сделать минимум 2 чтения - из x[n] и y2[n], плюс затраты на синхронизацию или что-то более умное

Ответ - y1 проще и быстрее
```

**2)** Предположим что размер warp/wavefront равен 32 и рабочая группа делится
на warp/wavefront-ы таким образом что внутри warp/wavefront
номер WorkItem по оси x меняется чаще всего, затем по оси y и затем по оси z.

Напоминание: инструкция исполняется (пусть и отмаскированно) в каждом потоке warp/wavefront если хотя бы один поток выполняет эту инструкцию неотмаскированно. Если не все потоки выполняют эту инструкцию неотмаскированно - происходит т.н. code divergence.

Пусть размер рабочей группы (32, 32, 1)

```
int idx = get_local_id(1) + get_local_size(1) * get_local_id(0);
if (idx % 32 < 16)
    foo();
else
    bar();
```

Произойдет ли code divergence? Почему?

```text
Ответ:

Так как размер warp-а равен 32 и координата x меняется чаще всего, то каждый warp будет целиком заполнять одну строку рабочей группы

Тогда idx = y + 32 * x. И тогда условие результат выражения idx % 32 < 16 будет одинаков для всех work item в warp (так как y будет одинаков)

Ответ - не произойдет
```

**3)** Как и в прошлом задании предположим что размер warp/wavefront равен 32 и рабочая группа делится
на warp/wavefront-ы таким образом что внутри warp/wavefront
номер WorkItem по оси x меняется чаще всего, затем по оси y и затем по оси z.

Пусть размер рабочей группы (32, 32, 1).
Пусть data - указатель на массив float-данных в глобальной видеопамяти идеально выравненный (выравнен по 128 байтам, т.е. data % 128 == 0). И пусть размер кеш линии - 128 байт.

(a)
```
data[get_local_id(0) + get_local_size(0) * get_local_id(1)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

(b)
```
data[get_local_id(1) + get_local_size(1) * get_local_id(0)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

(c)
```
data[1 + get_local_id(0) + get_local_size(0) * get_local_id(1)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

```text
Ответ:

Координата y у всех work item в рамках одного warp снова одинакова. Кэш-линия вмещает 32 float-а

(a) Индекс будет расти линейно, поэтому запишем все значения в одну линию - это coalesced. Будет 32 записи кэш-линий.

(b) Индекс растет нелинейно (x умножается на 32), поэтому будем "скакать" по памяти - это не coalesced. Для каждого значения придется писать индивидуальную кэш-линию, поэтому каждый warp запишет 32 кэш-линии. Тогда на всю work group будет 1024 записей кэш-линий

(c) Индекс растет линейно, поэтому это coalesced. Однако из-за сдвига 1 из 32 байт, которые work item должен записать, всегда будет попадать в соседнюю кэш-линию. То есть каждый work item должен записать 2 кэш-линии. Тогда всего будет 64 записи кэш-линий
```
