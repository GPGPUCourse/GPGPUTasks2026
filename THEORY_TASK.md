**1)** Пусть на вход дан сигнал x[n], а на выход нужно дать два сигнала y1[n] и y2[n]:

```
 y1[n] = x[n - 1] + x[n] + x[n + 1]
 y2[n] = y2[n - 2] + y2[n - 1] + x[n]
```

Какой из двух сигналов будет проще и быстрее реализовать в модели массового параллелизма на GPU и почему?

Ответ: y1[n] вычислется быстрее, чем на y2[n], потому что вычисление y2[n] требует ждять подсчета предыдущих двух значений, когда расчет y1[n] может производится параллельно.

**2)** Предположим что размер warp/wavefront равен 32 и рабочая группа делится
на warp/wavefront-ы таким образом что внутри warp/wavefront
номер WorkItem по оси x меняется чаще всего, затем по оси y и затем по оси z.

Напоминание: инструкция исполняется (пусть и отмаскированно) в каждом потоке warp/wavefront если хотя бы один поток выполняет эту инструкцию неотмаскированно. Если не все потоки выполняют эту инструкцию неотмаскированно - происходит т.н. code divergence.

Пусть размер рабочей группы (32, 32, 1)

```
int idx = get_local_id(1) + get_local_size(1) * get_local_id(0);
if (idx % 32 < 16)
    foo();
else
    bar();
```

Произойдет ли code divergence? Почему?

Ответ:
Здесь происходит code divergence. Так как размер группы 32, то в варпе get_local_size(1) будет равняться какому-то y, а get_local_size(0) будет варьироваться от 0 до 31. Посчитав для каждого возможных y, можно увидеть что ровно половина варпа выолняет foo и вторая половина выполняет bar. Таким образом, в варпе работает ровно половина потоков.

**3)** Как и в прошлом задании предположим что размер warp/wavefront равен 32 и рабочая группа делится
на warp/wavefront-ы таким образом что внутри warp/wavefront
номер WorkItem по оси x меняется чаще всего, затем по оси y и затем по оси z.

Пусть размер рабочей группы (32, 32, 1).
Пусть data - указатель на массив float-данных в глобальной видеопамяти идеально выравненный (выравнен по 128 байтам, т.е. data % 128 == 0). И пусть размер кеш линии - 128 байт.

(a)
```
data[get_local_id(0) + get_local_size(0) * get_local_id(1)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

Аналогично предыдущему вопросу предположим, что get_local_size(1) = y среди всего варпа (т.к. размер варпа и размерность рабочей группы равны).
Тогда мы выбираем индексы get_local_id(0)*(y+1). Stride между запросами потоками равен y+1, а значится чем больше y+1, тем больше кэша и соответствено кэш линий будет воспользоваться. Т.к. размер рабочей группы 32, то минимальный индекс 0*(y+1)=0 и максимальный индекс 31*(y+1). Соотвествено кол-во кэш линий это округление вверх от 31*(y+1)/128. Для y=31 мы задействуем целых 8 кэш линий! Так что это не coalesced

(b)
```
data[get_local_id(1) + get_local_size(1) * get_local_id(0)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?


Аналогично предыдущему вопросу предположим, что get_local_size(1) = y среди всего варпа (т.к. размер варпа и размерность рабочей группы равны).
Тогда мы выбираем индексы y*(get_local_id(0)+1). Stride между запросами потоками равен y, а значится чем больше y, тем больше кэша и соответствено кэш линий будет воспользоваться. Т.к. размер рабочей группы 32, то минимальный индекс y*(0+1)=y и максимальный индекс y*(31+1)=32*y. Соотвествено кол-во кэш линий это округление вверх от (32*y-y)/128=31*y/128. Для y=31 мы задействуем целых 8 кэш линий! Так что это не coalesced

(c)
```
data[1 + get_local_id(0) + get_local_size(0) * get_local_id(1)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?


Аналогично предыдущему вопросу предположим, что get_local_size(1) = y среди всего варпа (т.к. размер варпа и размерность рабочей группы равны).
Тогда мы выбираем индексы 1+get_local_id(0)*(y+1). Stride между запросами потоками равен y+1, а значится чем больше y, тем больше кэша и соответствено кэш линий будет воспользоваться. Т.к. размер рабочей группы 32, то минимальный индекс 1+0*(y+1)=1 и максимальный индекс 1+31*(y+1)=31*y+32. Соотвествено кол-во кэш линий это округление вверх от (31*y+32-1)/128=31*(y+1)/128. Для y=31 мы задействуем целых 8 кэш линий! Так что это не coalesced
